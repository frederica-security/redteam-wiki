# 0day漏洞 - 危险来源于未知

### 前世今生 {#前世今生}

0day漏洞几乎与黑客技术一同诞生。最早的黑客在那些黑框框古老程序中挖掘缺陷，并利用它们。因此早期的0day漏洞往往是指二进制层面的漏洞，尤其是内存层面的漏洞（堆栈溢出等）。<br> 但是现代软件架构中，Web应用极大取代了传统的客户端应用程序，即使使用客户端也往往是一些高度依赖后端Web服务的移动端应用（手机APP）。因此现在的0day往往是Web应用的漏洞。二进制0day式微的另一个原因是现代软件和操作系统具有内存层面的各种保护手段（例如ASLR，DEP/NX），并且二进制程序本身也愈发安全。

### 矛与盾 {#矛与盾}

0day漏洞在过去常常被神化，被认为是无法防御的，一旦攻击者祭出0day漏洞就意味着系统权限失守。但是如今的网络安全防御体系足以应对一定程度的0day攻击。

举个例子：小黑挖掘了某OA系统的SQL注入漏洞，并构造了对应payload，可以一键查询出管理员密码。但是在渗透过程中他使用该0day攻击时，对方系统的WAF（网站防火墙设备）**检测到SQL注入关键字特征**，直接拦截并在控制台产生告警。防御者查看控制台，发现是陌生的payload，很显然这台临时部署的廉价WAF捕获到了0day。小黑攻击失败，并折损了0day。

又或者另一种情况：小黑挖掘了更加精妙的0day漏洞，这个0day漏洞起源于鉴权代码中的逻辑缺陷，导致可以未授权访问到后台的某个反序列化接口。同时，这段反序列化数据经过特定编码，导致其原有特征不明显，显然此时安全设备是捕获不到的。他发起攻击并执行了whoami。页面返回了administrator，说明他实现了管理员权限远程命令执行。但是由于这个过程导致javaweb进程非常唐突地拉起cmd.exe并执行了whoami命令（这种行为非常诡异），被部署在主机上的agent型安全监测设备**捕获到异常行为**，并产生告警。防守方启动应急响应流程，小黑立刻被踹出内网。随后防守方通过日志分析，找到了对应payload，小黑0day数量再次-1。

当然了，回顾这个过程，我们会发现，如果小黑拥有先进的规避技术，对payload进行足够的处理，并且在攻击成功后更加谨慎，那么这可以成为一次成功的0day攻击。

### 掌控0day {#掌控0day}

如果我们需要一个自己的有效0day，Web代码审计的技术是不可或缺的。无论是传统的SQL注入/IDOR等漏洞，还是反序列化，都需要考虑在内。同时，如果是一些高度集成于特定系统的代码，例如安全设备（没错，安全设备本身也经常出现漏洞），或者某些带有安装包的一键部署式应用（就是那种连数据库和jdk都打包的巨大安装包），那么就还可以考虑系统配置缺陷，例如Web中间件配置不良造成某种特性，结合代码中的缺陷来综合构造payload。<br> 同时，由于前面的案例，不难发现，在真实场景应用0day前还需要考虑对方的安全解决方案（各种软件/硬件安全产品），需要对payload做良好处理，避免白给。<br> 同时，记住，0day往往是最终解决方案，要有将其作为昂贵消耗品的觉悟，如果能使用Nday/钓鱼达成目标，那么就不应当使用0day。<br> 一个折中的方案其实是使用1day或者比较新的nday——互联网上并不会时刻能查询到全部的漏洞信息，很多时候并没有公开exp，需要自己根据安全公告反推漏洞信息，甚至对安全补丁进行逆向分析。这种方式得到的漏洞虽然不是0day，但是由于时间差较短，仍然非常有效。
