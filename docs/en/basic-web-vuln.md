# 传统漏洞 - 古老但有效

## 传统Web漏洞 {#传统web漏洞}

Web漏洞的类型浩如烟海（SQLInjection，XSS，SSRF，CSRF，LFI，IDOR……），但是其中有些漏洞特别有利于**获取权限**。这一切就像是，一栋房屋可能存在许多问题，但是如果你想要**潜入**它，那么就不能执着于研究它是否存在水管泄露或者墙纸脱落这样的问题（*虽然它们的确是问题*），而是应该研究它是否有**门窗没有上锁**。

### SQL注入 {#sql注入}

#### 它如何诞生 {#它如何诞生}

***古老但有效*** 的一个经典例子。在现代Web应用中，数据库基本上是不可或缺的。你每天打开手机，访问各种APP的时候，它们的后端会去自己的数据库里查找许多信息，例如你是否拥有账号，账号是否有VIP，是否被封号……然后你访问APP中的页面或者视频，那么后端会去搜索数据库中你查询的内容，并且返回到你手机里的APP上，这样你就能看到自己想看到的内容了。

Web后端是如何与数据库交互的？答案是通过SQL。<br> 目前市面上有许多数据库，有商业的也有开源免费的。最常见的是mysql和mssql和oracle等。但是它们都能够使用SQL进行操作，其区别只是添加了各自的额外特性，因此SQL是一种通用查询语言。

来看一个例子：<br> `select * from users where id = 1;`<br> 在数据库中执行，数据库会去users数据表中寻找id为1的用户。<br> 数据表顾名思义类似于一张表格，例如一张表可能有id，username，password三个字段，然后其中有几十行信息，表示有几十个用户。<br> 例如，下面就是一张简单的users数据表：

| id | username | password |
| --- | :---: | ---: |
| 1 | admin | 123456 |
| 2 | xiaoming | 114514 |
| 3 | guest | 114514 |

那么安全问题从何而来？问题在于，为了业务需求，很显然需要根据用户输入来改变SQL语句，例如我作为用户试图访问`http://某个网站/news.php?id=1`的时候，后端执行了：<br> `select content from news where id = 1;`<br> 这样就可以返回编号为1的文章内容。<br> 而id=2的时候：<br> `select content from news where id = 2;`<br> 就会返回另一篇文章。<br> 但是如果有***坏家伙***访问了`http://某个网站/news.php?id=1 union select 1,2,(select password from users where id=1)`

那么本来应该查询news数据库的Web后端，将有可能会去users表查询id为1的用户的密码，并显示在页面上。<br> 此时的后端代码大致是这样的（有漏洞，大家不要学）：

```text
// 【风险点】：直接从 URL 参数获取 id，没有进行任何过滤或类型转换
$id = $_GET['id'];

// 【核心漏洞】：SQL 语句通过字符串拼接构造
// 正常的预期是：SELECT content FROM news WHERE id = 1
// 攻击者输入：1 UNION SELECT password FROM users WHERE id = 1
$sql = "SELECT title, content FROM news WHERE id = " . $id;

$result = $conn->query($sql);
```

于是造成了安全隐患。最关键的是，真实的攻击不仅可以查询数据库，由于能够执行任意SQL语句，攻击者有可能利用数据库特性尝试获取服务器权限！

---

但是，这是非常古老的场景。现代Web开发普遍采用持久层框架，例如Mybatis等，而不是通过jdbc之类的方式去手动操作数据库。<br> **那么，就安全了……吗？**

来看这样一段mybatis xml：

```text
<select id="searchNews" resultType="News">
    SELECT id, title, content
    FROM news
    WHERE title LIKE '%${keyword}%'
</select>
```

这是一段典型的模糊查询功能的实现，keyword由用户输入，最终被拼接到SQL语句中。许多程序员初步了解可以使用mybatis的#{参数}去避免SQL注入，但是由于实现模糊查询的时候需要提供灵活性，因此还是使用了${参数}的形式，并最终导致SQL注入。

---

#### 危害：从数据泄露到远程命令执行 {#危害从数据泄露到远程命令执行}

SQL语句不仅可以执行数据查询，根据数据库的不同，它能够实现**远程命令执行**。<br> 在Linux系统中，一般使用Mysql数据库，mysql数据库可以通过SQL语句写入文件，攻击者将恶意代码写入Web目录中，从而实现远程控制。即使无法写入Web目录，还可以通过UDF提权等高级手法直接获取服务器权限。<br> 在Windows中，常见MS SQLServer数据库。这种数据库拥有非常多存在安全隐患的特性。例如众所周知的xp_cmdshell存储过程，攻击者可以执行SQL语句启用该功能，然后直接在服务器上执行系统命令。即使有些管理员出于安全考虑而直接卸载了该功能，攻击者仍然可以利用`.NET CLR`从内存层面加载C#代码来执行恶意命令，这个攻击过程甚至是**无文件攻击**（不需要接触硬盘，不创建文件）……<br> 其他数据库也存在许多敏感特性，因此最重要的是从源头解决SQL注入问题，即从代码层面做好防御。

### 任意文件上传 {#任意文件上传}

#### 从asp到Springboot {#从asp到springboot}

经典的安全问题。早期许多网站是php或者jsp之类的脚本语言编写的（也有asp，但是那个也太古老了），如果在文件上传功能上不加防御，那么攻击者可以上传自己的代码，从而执行想要的功能。<br> 例如一个php编写页面的网站，我传了自己的php格式文件上去，那么访问对应页面就能执行代码。

猜猜现代Web应用是怎么解决这个问题的～<br> 答案是没有解决……而是直接把脚本语言整个丢掉了。<br> 现在的Web应用往往是直接预先编译再执行的（例如Springboot单文件项目，以及`.NET Core`，或者Golang之类的），即使上传了脚本也没法解析执行，脚本文件到了服务器上相当于普通的文本文件……

那么就安全了……吗？<br> 答案是～并没有。<br> 在特定情况下，如果文件上传的位置是可控的，那么攻击者可能会尝试把文件传到系统目录里，例如定时任务或者SSH公钥，一样能接管服务器。

于是代码层面必须考虑文件名是否存在路径穿越（比如说`../../../1.txt`）。

#### 现代文件上传攻击 {#现代文件上传攻击}

现在安全了吗？<br> 也没有。

想象一下，网站上有个功能允许用户上传压缩包，网站会自动解压并读取其中内容。<br> 有坏家伙在压缩包里面写了`../../../1.txt`，但压缩包本身的名字是普通无害的1.zip<br> 于是解压的那一刻，这个文件被释放到了网站外面。。。。<br> 这种攻击叫做***zip-slip***。<br> 悲剧的是，目前许多语言（例如java）并没有提供很好的zip实现，许多人在凭感觉来编写文件解压功能，于是这种攻击在近些年成为了一种先进的突破手段。

#### 一劳永逸 {#一劳永逸}

这个词其实不适合出现在安全领域，因为很少有真正一劳永逸的方案。不过至少面对这种漏洞，已有的最佳方案是把文件上传功能交给云服务厂商——其实就是把文件上传到云端存储桶上。这样，即使代码存在问题，也很难影响到Web服务器自身，毕竟文件根本没传到Web服务器上。<br> 但是这带来了新的，关于云的安全问题……此处就不展开了，想必各位可以有自己的一些思考。
